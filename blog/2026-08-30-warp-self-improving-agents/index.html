How Warp Built Self-Improving Agents Using File-Based Skills

Warp's self-improving agent architecture uses two file-based skills and human feedback loops to turn one-off agent runs into systems that compound capability over time. A practical pattern for any team building on MCP and the Claude Platform.

Ashrey | The Agent Lab

Most AI agents today are stateless. They run, produce output, and forget everything the moment the session ends. The next run starts from zero. Warp, the AI-powered terminal used by 800,000 developers, hit this wall with their internal code review agent. Engineers complained about unhelpful comments and low-quality output. Stopgap fixes — rewriting prompts by hand, expanding AGENTS.md — helped briefly but did not scale.

The core problem: feedback to an agent typically disappears when the session closes, removing critical context from the agentic loop. Warp's solution, detailed in their recent blog post, is a self-improving agent architecture built on file-based skills. The pattern is simple, reproducible, and works on the Claude Platform today.

The Two-Skill Architecture

Warp evolved a self-improving agent consisting of two skills with human feedback between them:

  • Inner / base skill — holds the functional domain knowledge and instructions. For code review, this skill contains the rules for what makes a good review, how to analyze a PR, what conventions to follow.
  • Outer / improver skill — an observer agent that runs on a schedule. It pulls accumulated human feedback, compares what the agent suggested against how humans responded, and proposes a small, focused edit to the base skill.

Because skills are plain files, agents are extremely good at updating them. These updates are reviewable, approvable, and mergeable through a normal PR workflow. Once merged, the next run of the inner skill inherits the improvement.

"File-based skills are a way of encoding knowledge for agents without putting that knowledge directly in the prompt, as something the agent can simply look up in the course of doing its job. The framework is really simple actually: there's the base domain-specific skill and then there's the improver skill that refines that domain-specific skill. This simplicity is the beauty of this approach." — Zach Lloyd, Warp founder

How the Loop Works in Practice

Warp's issue triage agent demonstrates the pattern end-to-end:

  1. Trigger: A GitHub Action fires an agent when someone files a new issue.
  2. Inner skill runs: The triage agent analyzes the issue for complexity and feasibility, assigns labels, and suggests a fix direction — all driven by the base skill file.
  3. Human feedback: A maintainer spots a missed label (e.g., ready to spec) and leaves a comment on the issue explaining what was missed and why.
  4. Outer skill runs: On a schedule, the improver agent (running in Warp's orchestration platform, Oz) authenticates to GitHub, runs a bundled Python script to pull recent issues carrying feedback, summarizes them into JSON, and reads that back into context.
  5. Skill edit proposed: The improver identifies concrete feedback signals and proposes the smallest edit to the inner skill — in this case, adding logic to apply ready to spec when an issue describes a real problem even if the exact UI shape is undefined.
  6. Human review & merge: The PR arrives with a description explaining which signals prompted the change. A human reviews, approves, and merges. The next triage run inherits the new knowledge.

That final human step closes the loop and keeps a person in control of what actually changes.

Best Practices from the Warp Team

Write principles, not rules

"Construct the skill as though you're instructing a smart person, not like you're programming a computer," Zach says. Direction like "Look for repeated code" provides better generalization than exhaustive variable-naming rules.

Explain the why

Providing the rationale behind a rule lets the agent reason about the problem instead of following rigid instructions, enabling better generalization to novel cases.

Make feedback effortless to give

Capture it where people already work — commenting directly on a PR or issue. Make it automatic with no extra submission step. "Low friction is what keeps signal flowing. If you make it too hard you're not going to get the feedback and you're not going to be able to improve the skill."

Keep skills small, use progressive disclosure

A good skill file isn't large; it references resource files and scripts rather than dumping everything into context at once. The bundled Python script that pulls GitHub feedback is itself a best practice — skills can reference resource files instead of writing fresh code on every run.

Feedback quality > volume, but volume helps

A small amount of detailed, domain-specific feedback from a senior engineer can outweigh lots of cursory thumbs-up/down because binary signals don't say why. "You can get really good signal even from a relatively small sample size if it's very detailed feedback from a person around domain specific knowledge that the agent otherwise would have no way of getting."

Put extra effort into the improver skill

The improver skill (the observer agent) is highly reusable across different use cases. "Outside of the domain-specific knowledge component, this is a fairly reusable mechanism — the improver skill for a code review agent is not that different from the improver skill for any other agent."

Key Questions to Answer Before You Build

Are you conflating skills with memory?

Skills are procedural and stable — "how to do X," run-agnostic, changed deliberately. Memory is auto-written by the agent at inference time and never stops changing. Don't mix them.

Do you need one improver loop, or one per agent?

Meet in the middle: a templated base loop captures the overlap across your agents, with domain-specific weights layered on. A handful of improvers can each own one; a hundred should share.

What happens when the feedback is wrong?

Assume it will be. Don't let the agent accept feedback blindly — give it context to sanity-check, filter whose input counts, and keep a human in the loop at either the filtering or final-review stage.

Is your domain verifiable?

Build the verification harness first, then let the agent tune against it: generate a reference corpus, compare output to reference, fix, repeat. If it isn't domain-verifiable, lean on deterministic evals against golden outputs wherever they exist. Where you must use human feedback, restrict it to domain experts — don't open the floodgates.

How do you know the whole system is improving?

Track the global metrics humans already eyeball — time to merge, contributor count, cost — and feed them back into the improver agents.

Why This Matters for MCP and Agent Builders

The Warp pattern maps cleanly to the Model Context Protocol. Skills are file-based, version-controlled, and tool-agnostic — they can be served via MCP resources, edited via MCP tools, and invoked by any compatible client. The self-improvement loop becomes a first-class primitive: an MCP server that exposes read_skill, write_skill, and list_feedback operations, with the improver agent as a scheduled MCP client.

For teams shipping on the Claude Platform today, the takeaway is immediate: you don't need a custom orchestration platform to start. The pattern works with file-based skills, GitHub Actions for scheduling, and the Claude API for the improver agent. Warp's Oz platform adds polish (auth, secrets, observability), but the architecture is portable.

Start with one agent. Give it a base skill. Add an improver that runs daily. Capture feedback where your team already works. Close the loop with a human review gate. Compound from there.
