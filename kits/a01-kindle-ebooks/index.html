Autonomous Kindle Publishing Pipeline

You can already get a chatbot to write you a book. That stopped being the hard part two years ago. The reason the book doesn't sell has almost nothing to do with the writing.

The problem this solves

If you've published on Kindle and it went nowhere, it was probably one of four things, and all four are predictable.

  • You picked the topic. You picked it because it interested you, or because a video said the niche was hot. Nobody checked whether real people type that phrase into Amazon's search box. Wrong topic plus perfect execution still equals zero sales.
  • You bulk-generated it. One prompt, 40,000 words, done in an hour. It repeats itself. The examples stop matching by chapter four. It circles the topic without ever telling the reader what to do.
  • The cover was an afterthought. A buyer decides in about a fifth of a second, at thumbnail size, in a grid, next to nine competitors. You designed it at full size and never looked at it small.
  • You published and stopped. Placement on its own earns pennies. A listing with no marketing on top is beer money.

Every one of those is a discipline problem, not a writing problem. So this isn't a prompt pack. It's a set of scripts that refuse to let the pipeline advance when a step has been skipped.

What is inside

  • Seven gates, built as mechanisms rather than advice. Demand validation, pain points as the specification, distribution decided up front, structure before generation, one section at a time, the cover as its own asset, then publish and market.
  • Six stdlib-only Python scripts, each with a --selftest. Demand probe, outline scaffold, section runner, cover check, title score, royalty model. No dependencies to install.
  • The demand gate fails closed. It probes Amazon's own Kindle Store autocomplete for real buyer phrases. If that source is unreachable it writes no evidence file and exits non-zero, and everything downstream refuses to start. A gate that quietly passes when it breaks isn't a gate.
  • A section runner with no batch mode. It hands out exactly one section at a time and refuses the next until the current one clears four named checks: repetitive, consistent, depth, voice. There's no flag to turn that off. It also warns you when the reviewer has never once failed a section, because a reviewer that never rejects anything is a rubber stamp.
  • A cover checker that reads the real image file, enforces Amazon's geometry rules and estimates whether the title is legible at thumbnail size, which is the size the buying decision is actually made at.
  • Claude skills and scheduled-task prompts for the demand gate, section writing, section review, metadata and the cover brief.
  • A standalone bootstrap prompt. Paste it into Claude and the whole pipeline rebuilds from that one file, with none of the others.
  • ECONOMICS.md, RISKS.md, VERIFY.md and HUMAN_STEPS.md. The verify file has real command transcripts. The economics file has explicit kill criteria for when to drop the whole thing.

The one fact that arguably pays for this on its own

On 7 July 2026 Amazon raised the ceiling for the 70% royalty option from 9.99 USD to 12.99 USD on Amazon.com. That ceiling had not moved since 2007. I verified it on Amazon's own eBook list price requirements page on 4 August 2026.

Essentially every guide, course, blog post and royalty calculator online still says 9.99. Using Amazon's published formula, a 1.2 MB file at 12.99 returns 8.97 USD of royalty per US sale, against 6.87 at 9.99. That's a 31% larger royalty per sale for changing one field on the upload form.

To be exact about what that number is and isn't: it's the royalty on a single sale, computed from Amazon's formula, and the included royalty_model.py --selftest reproduces Amazon's own worked example to the cent. It is not a forecast. How many copies your book sells is unknown, and the script deliberately ships with no default for copies per month so it can't accidentally produce one.

What you have to do yourself

Five steps. About 75 minutes once, then roughly 10 minutes per book. Each one is listed in HUMAN_STEPS.md with the reason an agent can't do it: the KDP account, the tax interview, the bank details, the pen name, and the upload itself.

The upload is the honest one. There is no KDP publishing API and there never has been. Not for you, not for large publishers. Every tool claiming KDP API access is driving the browser form, and driving a logged-in Amazon account with a bot risks the account, which is the whole business. So this kit doesn't do that, and tells you not to either.
