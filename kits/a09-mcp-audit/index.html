MCP Reliability Audit Kit

You can already audit an MCP server by hand. The problem is doing it the same way twice, and having something a client will pay for at the end of it.

The problem this solves

MCP is how agents reach tools and data, which makes an MCP server a genuinely sensitive piece of infrastructure. The documented failure modes are real: tool descriptions that carry prompt injection, over-scoped tokens, confused-deputy problems, tool shadowing. Any competent engineer can spot some of these by reading the code. Very few can do it identically on the fifth server, write it up in a form a client will act on, and charge for it.

This kit is the repeatable version of that. It wraps mcp-doctor, an open source zero dependency CLI with 11 documented checks, and adds the parts that turn a scan into an engagement: scope and authorisation, severity triage, a client ready report template, and a weekly pipeline.

What is inside

  • Two Claude skills. One runs the audit end to end. One turns raw findings into a client ready deliverable with reproduction steps and prioritised remediation.
  • A scheduled task prompt that runs the offering on a weekly cadence.
  • A standalone bootstrap prompt. Paste it into Claude and start auditing with none of the other files.
  • ECONOMICS.md with the arithmetic, break even, and explicit kill criteria for when to drop the offering.
  • RISKS.md and VERIFY.md. The verification file contains real command transcripts, not illustrations.

What you have to do yourself

Four steps, about 20 minutes once and 15 minutes a week. They are listed with timings in HUMAN_STEPS.md, each with the reason an agent cannot do it for you. The one that is not negotiable: you need written authorisation before auditing a server you do not own. The kit refuses to help you skip that.

One thing you should know before buying

MCP spec revision 2026-07-28 removed the initialize handshake and the session id header. mcp-doctor 0.1.0 still sends the older protocol version, so a server that has fully migrated will fail its health check for protocol reasons rather than because anything is wrong with it. That is gated explicitly in the run skill, required as a limitations line in every report the kit generates, and it is kill criterion seven in ECONOMICS.md. I would rather you read that here than discover it in front of a client.
